SwiftData Rules

How FitTap will keep your workouts on the phone: who is allowed to touch the database, how a workout session lives, and why each choice was made. Plain English, one page.

Status: planned, nothing built yet Agreed 29 Oct 2026 iOS 27
The big picture

Five layers, and only one of them touches the database

Think of it as a building. Each floor only talks to the floor directly below it. The database sits in the basement, and only one person has the key.

Views
What you see. They show values and report taps. They never load or save anything.
↓ taps go down, values come up
Screen models
The brain of one screen. Asks a store for data, decides what happens on a tap.
↓
Stores
Shared, always-up-to-date lists: exercises, workouts, sessions, profile. Every screen reads the same store, so two screens never disagree.
↓ the only floor that calls the manager
SwiftDataManager
The one key holder. Translates between the app's models and saved entities, enforces the session rules, saves after every change.
↓
SwiftData
The database file on the phone. Ready for iCloud later, with sync switched off for now.

The two hard rules

  • Only the manager touches SwiftData. No view, screen model or store imports it.
  • The manager goes into stores only. Screen models talk to stores, never to the manager.
Two kinds of models

The app works on copies; the database keeps entities

Local models

The plain structs the app already has: WorkoutSession, WorkoutTemplate, Exercise. Screens edit these freely.

Editing a copy is why Cancel, the discard alert and "Save stays grey until something changes" keep working.

⇄manager
translates

Entities

What actually gets saved, named with Entity on the end: WorkoutSessionEntity, ExerciseEntity.

Nobody outside the manager ever sees one.

How a workout session lives

Planned sessions follow, started sessions freeze

A real week with your Push Day (bench, shoulder press, push-ups):

Monday
follows Push Day

You plan Push Day for Friday. Friday holds no copy yet. It simply points at Push Day.

Wednesday
still follows

Your shoulder hurts, so you edit the general Push Day in the Workouts tab: shoulder press out, dips in. Friday now shows dips automatically.

Thursday
its own copy

Optional: you open Friday's session from Home and tap Edit. Friday takes its own copy right then and gets your change. Only Friday changes; the general Push Day doesn't.

Friday
frozen

You press Start. Friday takes its copy (if it hasn't already) and freezes. Whatever you log stays exactly as you did it.

Later
history stays true

You put shoulder press back into Push Day, or delete Push Day altogether. Friday's log still says dips. Planned sessions of a deleted workout take a copy first, so they stay on your calendar.

Planned

Shows whatever the general workout looks like right now.

Edited from Home

Takes its own copy and stops following.

Started

Copied and frozen for good. This is history.

Every session remembers which workout it came from by that workout's id, so stats can still say "Push Day: 8 sessions" even after Push Day is deleted.

What gets saved, and how

Every set is its own row

Stats and the future coach ask questions like "bench press top weight over two months". The database can only answer that quickly if each set is a separate row it can search. A session is saved as a small tree:

Session · Push Day, Friday
Exercise entry · Bench Press · felt Medium (points at the exercise by id; "felt" is the optional rating from the "How did it feel?" tab)
Set · 10 reps · 60 kg · logged 18:04
Set · 8 reps · 62.5 kg · logged 18:07
Exercise entry · Running (duration, speed, distance stored right on the entry)

Deleting a session deletes its entries and sets with it. Saving compares sets by id: changed ones update, new ones are added, removed ones go. Nothing is thrown away and rebuilt, so history keeps its identity.

The other decisions

Smaller choices, and the reason for each

Built-in exercises get fixed ids

All 46 are copied into the database on first launch, each with an id that never changes.

The same Bench Press on every phone; an app update can add new ones; a future online catalog (Supabase) can reuse the ids.

Ready for iCloud, sync off

Every saved value has a default, every link between entities is optional, nothing is "must be unique".

iCloud sync and the Watch are planned. Building it this way now means turning sync on later needs no data conversion.

Profile kept simple

One saved row: name, age, current weight.

Simple first. Home's header shows the weight without "this month's change" until weight history exists.

Version 1 until release

The database layout is "version 1" and can change freely until real data exists (first release, TestFlight, or your own real workouts).

After that, every change becomes a planned upgrade step, so nobody's data breaks.

Saved right away

The manager saves after every change instead of waiting for autosave.

Autosave waits a few seconds and doesn't run when Xcode stops the app. A logged set should never be lost.

Links by id, not by connection

A set points at its exercise, and a session at its workout, by a plain id.

A database connection would be wiped when the exercise or workout is deleted, and history would lose its grouping.

How we build it

Build order

Each step is finished, compiles, and is staged before the next one starts. You check how it looks and behaves on the phone.

  1. Confirm Apple's iCloud rules, and decide the mock data question below.next
  2. Give the 46 built-in exercises their fixed ids.to do
  3. Create the six entities, version 1, and an empty upgrade plan.to do
  4. Write the translation between local models and entities.to do
  5. Build the manager and register it.to do
  6. Move the exercise store onto the manager.to do
  7. Move the workout store onto the manager.to do
  8. Move the session store onto the manager. Logged sets save instantly.to do
  9. Edit from Home changes only that day's session (today it changes the general workout).to do
  10. Start freezes the session.to do
  11. Profile comes from the database; header shows weight only.to do
  12. Mock data, once decided.to do
Parked · decide before building

Mock data

The proposal: test builds fill the real database once with three weeks of sample sessions; release builds only add the built-in exercises; previews keep using their sample structs; and a test-only "reset data" button refills everything around today's date (because sample dates go stale after a week).
